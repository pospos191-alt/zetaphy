# SWD Quantum — ตู้เซฟกันคอมพิวเตอร์ควอนตัมสำหรับ SWD บน Solana

ฉบับภาษาอังกฤษ (รายละเอียดทางเทคนิคครบ): [SWD_QUANTUM.md](SWD_QUANTUM.md)

> **สถานะ (2026-11-09): ร่าง ยังไม่ผ่าน audit ยังไม่ได้ deploy ที่ไหนเลย**
> ลำดับ: เทสต์บนเครื่อง (CI) → devnet → **audit อิสระ (รวมส่วนคริปโต)** →
> mainnet โดยต้องทำให้โปรแกรม **แก้ไขไม่ได้อีก (immutable)** ก่อน
> ห้ามเอา SWD จริงใส่ตู้เซฟก่อนผ่าน audit

## 1. ปัญหาคืออะไร (ภาษาง่าย ๆ)

- ที่อยู่กระเป๋า Solana ทุกใบ **คือ** กุญแจสาธารณะแบบ Ed25519 ถ้าวันหนึ่งมี
  คอมพิวเตอร์ควอนตัมที่ใหญ่พอ (เรียกวันนั้นว่า "Q-day") มันจะคำนวณกุญแจลับ
  ย้อนจากที่อยู่ได้ แล้วโอนเงินออกไปได้ วันนี้ยังไม่มีใครทำได้ และไม่มีใครรู้ว่า
  จะเกิดปีไหน (หน่วยงานสหรัฐฯ NIST วางแผนไว้ราวปี 2030 ขึ้นไป)
- บน Solana กุญแจเปิดเผยตั้งแต่วันแรก (เพราะมันคือที่อยู่) จึงไม่มี "กระเป๋า
  ที่ยังไม่เคยใช้ = ปลอดภัยกว่า" แบบ Bitcoin/Ethereum
- แต่ "ฟังก์ชันแฮช" (เช่น SHA-256) ยังทนคอมพิวเตอร์ควอนตัมได้ ลายเซ็นที่สร้าง
  จากแฮชล้วน ๆ จึงยังปลอดภัย — ตู้เซฟนี้ใช้ลายเซ็นแบบนั้น

## 2. อะไรปลอดภัย อะไรไม่ปลอดภัย

| สิ่งของ | ปลอดภัยหลัง Q-day ไหม |
|---|---|
| SOL และโทเคน (เช่น SWD) **ที่อยู่ในตู้เซฟ SWD Quantum** | **ปลอดภัย** ถ้าโปรแกรมถูกล็อกไม่ให้แก้ไขแล้ว และเจ้าของเก็บ seed ดี ๆ ไม่มีกุญแจ Ed25519 ตัวไหนโอนออกได้ |
| กระเป๋าปกติ (Phantom, Solflare, Ledger ฯลฯ) | **ไม่ปลอดภัย** ยังเป็น Ed25519 เหมือนเดิม ของที่อยากเก็บไว้ยาว ๆ ให้ย้ายเข้าตู้เซฟก่อน Q-day |
| ทะเบียน "คำมั่นกุญแจ PQ" (ข้อ 6) | ไม่ได้ป้องกันเงินโดยตรง เป็น **หลักฐาน** ให้ SWD/ZETAPHY ใช้ยืนยันสิทธิ์ย้ายเงินในอนาคต |
| ตู้เซฟ ขณะที่โปรแกรมยังมีกุญแจอัปเกรด | **ปลอดภัยเท่ากับกุญแจอัปเกรดนั้น** (ซึ่งเป็น Ed25519) ใครคุมกุญแจนี้เปลี่ยนโปรแกรมได้ ต้องล็อกโปรแกรมก่อนใช้จริง |
| โทเคนที่ mint มีสิทธิ์ "แช่แข็ง" (freeze authority) | เจ้าของสิทธิ์นั้น (กุญแจ Ed25519) **แช่แข็ง** โทเคนในตู้ได้ แต่ **เอาไปไม่ได้** ส่วนโทเคนที่มี "ผู้แทนถาวร" (เอาไปได้) ตู้จะไม่รับฝาก |
| ตัวเครือข่าย Solana เอง | ถ้าควอนตัมเจาะกุญแจของ validator ได้ เครือข่ายอาจหยุดหรือแยก ตู้เซฟกันการขโมยกุญแจ ไม่ได้กันเครือข่ายล่ม |

## 3. ตู้เซฟทำงานอย่างไร

- **กุญแจใช้ครั้งเดียว (Winternitz / LM-OTS มาตรฐาน RFC 8554 + NIST SP 800-208)**:
  ลายเซ็นหนึ่งครั้งเปิดเผยข้อมูลบางส่วนของกุญแจ เห็นลายเซ็น **หนึ่ง** อัน
  ปลอมอันอื่นไม่ได้ แต่ถ้าเซ็น **สองข้อความต่างกัน** ด้วยกุญแจเดียว คนอื่น
  เอามารวมกันปลอมได้ — กุญแจแต่ละดอกจึงเซ็นได้ครั้งเดียว
- **เปลี่ยนกุญแจทุกครั้งที่ถอน**: ทุกการถอนต้องระบุ "กุญแจดอกถัดไป" ไว้ในข้อความ
  ที่เซ็น โปรแกรมตรวจลายเซ็น ส่งเงินตามจำนวนที่เซ็นเป๊ะ ๆ แล้วเปลี่ยนเป็น
  กุญแจดอกใหม่ทันทีในคำสั่งเดียวกัน ที่อยู่ตู้เซฟไม่เปลี่ยน
- **ที่อยู่ตู้เซฟ** คำนวณจาก "แฮช" ของกุญแจดอกแรก จึงไม่มีอะไรให้ควอนตัมเจาะ
- **seed เดียว (32 ไบต์) สร้างได้หลายตู้** (ตู้ที่ 0, 1, 2, …) และกุญแจทุกดอก
- คนจ่ายค่าธรรมเนียมเป็นใครก็ได้ เขาแค่จ่ายค่า fee ทำอะไรนอกเหนือจากที่เจ้าของ
  เซ็นไว้ไม่ได้
- ตู้เซฟ **ปิดไม่ได้** โดยตั้งใจ (ถ้าปิดได้ คนอื่นจะเปิดตู้ที่อยู่เดิมใหม่ด้วยกุญแจ
  ดอกแรกที่ใช้ไปแล้ว ซึ่งอันตราย) ค่าเช่าพื้นที่ 0.0015 SOL จึงอยู่ในตู้ตลอดไป

สิ่งที่โปรแกรมกันไว้ (มีเทสต์ทุกข้อ): ส่งลายเซ็นเก่าซ้ำ, เซ็นซ้ำด้วยกุญแจเดิม,
แก้ตัวเลข/ปลายทาง/กุญแจถัดไปในข้อความ, เอาลายเซ็นไปใช้กับตู้อื่น, ใส่ mint
หรือโปรแกรมโทเคนผิด, โทเคน Token-2022 ที่หักค่าธรรมเนียมตอนโอน/มีโค้ดแทรก
(transfer hook)/มีผู้แทนถาวร, โอนไม่ครบจำนวน, ขโมยค่าเช่า, ปิดบัญชีไปที่อื่น

## 4. กฎสำหรับผู้ใช้ (สำคัญมาก)

1. **seed 32 ไบต์ = ตู้เซฟ** ใครได้ seed ไปก็ถอนได้ ถ้า seed หาย เงินหายถาวร
   ไม่มีใคร (ทั้ง SWD และ ZETAPHY) กู้คืนให้ได้ เก็บแบบออฟไลน์ (กระดาษ/แผ่นโลหะ)
   สองที่ ห้ามเก็บในเบราว์เซอร์ และไม่ใช่ recovery phrase ของ Phantom
2. **กุญแจหนึ่งดอก ข้อความเดียว**: เซ็นการถอนแล้ว ต้องส่ง "ลายเซ็นเดิมนั้น"
   เท่านั้น ถ้าธุรกรรมไม่เข้า ให้ **ส่งลายเซ็นเดิมซ้ำ** (เปลี่ยนคนจ่าย fee หรือ
   blockhash ได้) ห้ามเซ็นการถอน "แบบอื่น" ด้วยกุญแจลำดับเดิมเด็ดขาด
3. สร้างคำสั่งถอนจากสถานะตู้ **ล่าสุดบนเชน** เสมอ (ไลบรารีทำให้อัตโนมัติ)
4. ฝากโทเคนผ่านคำสั่ง `deposit_token` (มันจะปฏิเสธโทเคนที่ไม่ปลอดภัยสำหรับตู้)
   ถ้าโอนโทเคนที่ถูกปฏิเสธเข้าตู้ตรง ๆ อาจถอนออกไม่ได้

## 6. ทะเบียน "คำมั่นกุญแจ PQ" (แบบ QuantumRescue ของ ZETAPHY)

**ทำอะไร**: วันนี้ (ตอนกุญแจ Ed25519 ยังเชื่อถือได้) กระเป๋าเซ็นบันทึกค่าแฮช

`keccak256("SWD QuantumCommit v1" ‖ ที่อยู่กระเป๋า ‖ แฮชของกุญแจ ML-DSA-44 ‖ รหัสลับ 32 ไบต์)`

ไว้บนเชน มีแค่แฮช ไม่มีใครรู้กุญแจหรือรหัสลับ การเปลี่ยน (หรือยกเลิก) จะมีผล
หลัง **7 วัน** (บน mainnet; devnet ใช้ 8 วินาทีเพื่อให้ลองได้) ระหว่างรอ อันเก่า
ยังมีผล ทุกการเปลี่ยนมี event ให้ตรวจย้อนได้

**เอาไว้ทำอะไร**: หลัง Q-day ทาง SWD/ZETAPHY จะประกาศ "เวลาตัด" ล่วงหน้า
เจ้าของกระเป๋าเปิดเผยกุญแจ ML-DSA และรหัสลับ พร้อมลายเซ็น ML-DSA ถ้าแฮชตรงกับ
อันที่มีผล ณ เวลาตัด ก็ยืนยันสิทธิ์ย้ายยอด (เช่น แจก SWD ตาม snapshot หรือรับยอด
บน ZETAPHY) ได้ — ทำนอกเชนหรือบน ZETAPHY

**ไม่ได้ทำอะไร**: ไม่ล็อกหรือย้ายเงินบน Solana, ไม่ตรวจลายเซ็น ML-DSA บนเชน,
ไม่กันคนร้ายควอนตัมถอนเงินออกจากกระเป๋าปกติหลัง Q-day ประโยชน์คือ คนร้ายที่
เจาะกุญแจได้ **หลัง** เวลาตัด หรือก่อนเวลาตัด **ไม่ถึง 7 วัน** แทนที่คำมั่นของ
เจ้าของไม่ได้ ต้องเก็บกุญแจ ML-DSA (seed ของมัน) และรหัสลับไว้ออฟไลน์ ถ้าหาย
คำมั่นก็ไร้ค่า

## 7. เทียบกับเชน ZETAPHY

ZETAPHY ใช้ลายเซ็น ML-DSA-44 (ใช้ได้หลายครั้ง) ทั้งบัญชี ตรวจที่ตัวเชนเอง
ส่วนบน Solana เราวัดแล้วว่า ML-DSA หนักเกินไป: กุญแจ+ลายเซ็นรวม 3,732 ไบต์
(ใหญ่กว่าขีดจำกัดธุรกรรม 1,232 ไบต์ 3 เท่า) และการแฮชแบบที่ ML-DSA ต้องใช้
(SHAKE) ไม่มีคำสั่งสำเร็จรูปบน Solana ต้องคำนวณเอง ครั้งละ ~11,400 CU และต้อง
ทำราว 100 ครั้ง (~1.1 ล้าน CU) ก่อนจะนับงานส่วนอื่น รวมแล้วเกินขีด 1.4 ล้าน CU
ต่อธุรกรรม ต้องแบ่ง 6–8 ธุรกรรมต่อการถอนหนึ่งครั้ง ไลบรารีสำเร็จรูปก็ใช้หน่วยความ
จำเกินที่ Solana ให้ จึงเลือกลายเซ็นแบบแฮช (LM-OTS) ที่จบใน **ธุรกรรมเดียว
~0.3 ล้าน CU** ลายเซ็นยาว 648 ไบต์

## 8. ขั้นตอน deploy บน devnet

```bash
solana-keygen new -o target/deploy/swd_quantum-keypair.json   # ห้าม commit (gitignore ไว้แล้ว)
anchor keys list   # เอา id ของ swd_quantum ไปใส่ใน Anchor.toml และ declare_id! ใน programs/swd_quantum/src/lib.rs
anchor build -p swd_quantum
anchor deploy -p swd_quantum --provider.cluster devnet
```

แล้วใช้ไลบรารี `integrations/swd-quantum-ts` สร้าง seed สำหรับ devnet เท่านั้น
เปิดตู้ ฝาก SOL และโทเคนทดสอบ ถอนหลาย ๆ ครั้ง ลองทะเบียนคำมั่น ใช้งานอย่างน้อย
1 สัปดาห์

**mainnet (หลังผ่าน audit อิสระเท่านั้น)**: build ด้วย
`anchor build -p swd_quantum -- --features mainnet` (หน่วงเวลา 7 วัน) →
deploy → **ล็อกโปรแกรม** ด้วย `solana program set-upgrade-authority <PROGRAM_ID> --final`
→ ค่อยเปิดให้ใช้กับเงินจริง เริ่มจากวงเงินเล็ก ๆ

## 9. ความเสี่ยงที่ยังเหลือ

- **ยังไม่ผ่าน audit** รวมถึงโค้ดคริปโต ต้องให้ผู้เชี่ยวชาญตรวจกับมาตรฐาน
  RFC 8554 / SP 800-208
- **กุญแจอัปเกรดโปรแกรม** เป็นความเสี่ยงใหญ่ที่สุดจนกว่าจะล็อก (`--final`)
- **ผู้ใช้ทำพลาด** คือจุดอ่อนหลัก: ทำ seed หาย หรือเซ็นการถอนสองแบบด้วยกุญแจ
  ลำดับเดียวกัน แอปกระเป๋าต้องจำว่า "เซ็นลำดับนี้ไปแล้ว" ก่อนส่ง
- ความแข็งแรงต่อควอนตัมต่อแฮชหนึ่งครั้งอยู่ที่ราว 96 บิต (ระดับเดียวกับ AES-192
  สูงกว่า ML-DSA-44) เลือกขนาดนี้เพื่อให้จบในธุรกรรมเดียว
- เจ้าของสิทธิ์แช่แข็งของ mint แช่แข็งโทเคนในตู้ได้
- ถ้า Solana ขึ้นราคา compute ในอนาคต กรณีแย่สุด (~0.95 ล้าน CU) ยังเหลือที่ราว 30%
- ทะเบียนคำมั่นจะมีประโยชน์ก็ต่อเมื่อมีกระบวนการยืนยันหลัง Q-day ซึ่งยังไม่ได้เขียน
