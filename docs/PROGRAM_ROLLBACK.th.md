# SWD AMM: ตรวจว่าโค้ดบนเชนเป็นของแท้ และย้อนรุ่นเมื่อถูกแฮ็ก (คู่มือสำหรับเจ้าของ)

## เข้าใจง่ายๆ ก่อน

ใครถือ **กุญแจอัปเกรด (upgrade authority)** ก็เปลี่ยนโค้ดของโปรแกรมบนเชนได้ทั้งหมด
ตามแผน กุญแจนี้อยู่ใน **Squads vault** ซึ่งต้องให้กรรมการเซ็นพร้อมกัน 2 ใน 3 คน
เครื่องมือชุดนี้มีไว้เพื่อ 3 เรื่อง

- **เห็น:** ทุกชั่วโมงระบบจะตรวจว่าโค้ดบนเชนเปลี่ยนหรือเปล่า และใครถือกุญแจอยู่ ถ้าผิดปกติจะส่ง Telegram และส่งอีเมลจาก GitHub
- **พิสูจน์ได้:** โปรแกรมถูก build ใน Docker ที่ล็อกเวอร์ชันไว้ ใครจะ build ซ้ำเองก็ได้ไฟล์เหมือนเดิมทุกไบต์ จึงเทียบได้ว่าโค้ดบนเชนตรงกับโค้ดที่เปิดเผยใน GitHub
- **ย้อนได้:** ถ้ารุ่นใหม่มีบั๊ก ก็เอารุ่นเก่าที่ตรวจแล้วกลับขึ้นไปได้ โดยกรรมการ Squads เป็นคนอนุมัติ

แต่ถ้า **คนร้ายได้กุญแจอัปเกรดไปแล้ว** เครื่องมือนี้ย้อนให้ไม่ได้ ทางป้องกันจริงคือรักษากุญแจของกรรมการให้ดี (ดูหัวข้อ "กุญแจหาย" ด้านล่าง)

| เครื่องมือ | ไฟล์ |
|---|---|
| build ที่ตรวจซ้ำได้ และปล่อยรุ่น (Release) | `scripts/verified-build.sh`, workflow `verifiable-build` (ทำงานเมื่อติด tag `program-v...`) |
| ตัวเฝ้าดูบนเชน (ทุกชั่วโมง) | `scripts/program-watch.mjs`, workflow `program-watch` |
| ย้อนรุ่น / ดูสถานะ | `scripts/rollback-program.sh` (แค่ "ซ้อม" จนกว่าจะใส่ `--execute`) |
| ปุ่มหยุดฉุกเฉิน | `yarn governance emergency-pause-v2-pool` |

## หยุด (pause) หรือ ย้อนรุ่น (rollback)?

- **หยุด** คือกดเบรกทันที ใช้เวลาไม่กี่วินาที คนถือกุญแจฉุกเฉิน (emergency key) กดได้คนเดียว
  การหยุดไม่ได้ย้ายเงินไปไหน แค่ห้าม swap / ฝาก / ถอน ชั่วคราว
  คนกดหยุด **เปิดกลับเองไม่ได้** การเปิดต้องผ่าน Squads และต้องรอ timelock อย่างน้อย 24 ชั่วโมง
- **ย้อนรุ่น** คือเปลี่ยนโค้ดกลับเป็นรุ่นเก่าที่ปลอดภัย ต้องให้กรรมการ Squads อนุมัติ และรอ time lock ของ Squads (ถ้าตั้งไว้)

**กฎทอง: หยุดก่อนเสมอ แล้วค่อยคิด**

| เกิดอะไรขึ้น | ทำอะไรก่อน | แล้วทำอะไรต่อ |
|---|---|---|
| เงินไหลออกผิดปกติ หรือมีคนแจ้งช่องโหว่ที่น่าเชื่อ | **หยุด** พูลที่เกี่ยวข้อง | ตรวจสอบ แล้วเลือกว่าจะย้อนรุ่นหรือแก้ไปข้างหน้า |
| บั๊กมาจาก **รุ่นล่าสุด** และรุ่นก่อนหน้าปลอดภัย | หยุด | **ย้อน** ไปรุ่นก่อนหน้าผ่าน Squads |
| บั๊กมีอยู่ **ทุกรุ่น** | หยุด | **แก้ไปข้างหน้า**: แก้โค้ด ให้ผู้ตรวจ (auditor) ดูซ้ำ ออกรุ่นใหม่ แล้วอัปเกรดผ่าน Squads |
| ตัวเฝ้าดูแจ้ง **"NOT any published release"** (โค้ดบนเชนไม่ตรงกับรุ่นไหนเลย) | หยุด แล้วถามกรรมการทุกคนว่า "มีใครอนุมัติอัปเกรดไหม" | ถ้าไม่มีใครอนุมัติ ให้ถือว่า vault ถูกเจาะ (ดู "กุญแจหาย") |
| ตัวเฝ้าดูแจ้งว่า **ผู้ถือกุญแจอัปเกรดเปลี่ยน** | หยุด แล้วประกาศเตือนผู้ใช้ทันที | ดู "กุญแจหาย" |
| บั๊กอยู่ที่หน้าเว็บอย่างเดียว | ปิดเว็บหรือย้อนเว็บ (Vercel / Cloudflare) | ไม่ต้องแตะโปรแกรม |

> ข้อควรระวัง: โค้ดรุ่นเก่าต้องอ่านข้อมูลบัญชีในปัจจุบันได้ ถ้ารุ่นใหม่เปลี่ยนรูปแบบข้อมูลไปแล้ว การย้อนอาจทำให้ข้อมูลพัง
> ก่อนย้อนทุกครั้งให้อ่าน release notes ของทุกรุ่นที่อยู่ระหว่างกลาง ถ้ามีการเปลี่ยนรูปแบบข้อมูล ให้ "แก้ไปข้างหน้า" แทน

## ลำดับขั้นหลังถูกแฮ็ก (ทำตามนี้)

1. **หยุดฉุกเฉิน (ภายในไม่กี่นาที):** คนถือกุญแจฉุกเฉินรันคำสั่ง
   `yarn governance emergency-pause-v2-pool <POOL> true true true --yes`
   แล้วขึ้นป้าย "ปิดปรับปรุง" บนเว็บ ห้ามเปิดพูลระหว่างเกิดเหตุ
2. **ตรวจสอบ (เป็นชั่วโมง):** รัน
   `bash scripts/rollback-program.sh status --cluster mainnet --program-id <ID> --url <RPC> --vault <SQUADS_VAULT>`
   ผลจะบอกว่าโค้ดบนเชนตรงกับรุ่นไหน ถ้าไม่ตรงรุ่นไหนเลยจะขึ้นว่า UNKNOWN CODE และบอกว่าใครถือกุญแจ
   เก็บลายเซ็นธุรกรรมของคนร้ายไว้ ติดต่อผู้ตรวจ แล้วตัดสินใจว่าจะย้อนไปรุ่นไหน หรือจะแก้ไปข้างหน้า
3. **เตรียมการย้อน:** รันคำสั่งเดิมแบบซ้อมก่อน (ไม่ใส่ `--execute`)
   `bash scripts/rollback-program.sh prepare program-vX.Y.Z --cluster mainnet --program-id <ID> --url <RPC> --vault <SQUADS_VAULT> --keypair ~/keys/ops-payer.json`
   ถ้าทุกอย่างถูกต้อง ค่อยรันซ้ำโดยเติม `--execute` สคริปต์จะถาม "yes" ก่อนทุกขั้น
   สคริปต์จะตรวจ hash ของไฟล์รุ่นนั้น 3 ทาง แล้วเขียนโค้ดลง "buffer" (ยังไม่มีผลกับโปรแกรม)
   จากนั้นตรวจ hash อีกรอบ และโอนสิทธิ์ buffer ให้ Squads vault
   กุญแจที่ใช้มีหน้าที่แค่จ่ายค่า SOL (ประมาณ 5.7 SOL ได้คืนเมื่ออัปเกรดเสร็จ) ไม่มีสิทธิ์พิเศษอะไร
4. **เสนอใน Squads:** สคริปต์จะพิมพ์ค่าที่ต้องใช้ออกมาให้ทั้งหมด ในแอป Squads ไปที่ Developers → Programs → เลือกโปรแกรม → Upgrade แล้วใส่ที่อยู่ buffer
   **กรรมการทุกคนต้องตรวจ hash ของ buffer บนเครื่องตัวเองก่อนกดอนุมัติ**
   (`solana program dump <BUFFER> buffer.so` แล้ว `bash scripts/verified-build.sh hash buffer.so`) เลขต้องตรงกับที่สคริปต์บอก
   อนุมัติให้ครบตามจำนวน แล้วรอ time lock ของ Squads จนครบ จึงกด Execute
   หมายเหตุ: timelock 24–48 ชั่วโมงของโปรแกรมใช้กับคำสั่ง governance เท่านั้น **ไม่ครอบคลุมการอัปเกรดโค้ด**
   ระหว่างที่รอ พูลยังหยุดอยู่ เงินของผู้ใช้จึงปลอดภัย
5. **ตรวจว่าตรงจริง:** รัน `status` อีกครั้ง hash ต้องตรงกับรุ่นที่ย้อนไป และผู้ถือกุญแจต้องยังเป็น vault
   จากนั้นตั้งตัวแปร `EXPECTED_HASH_MAINNET` ใน GitHub ให้เป็น hash ของรุ่นนั้น ตัวเฝ้าดูจะได้ไม่เตือนซ้ำ
   (ลบตัวแปรนี้ทิ้งเมื่อออกรุ่นใหม่แล้ว)
6. **เปิดพูลกลับ (อย่างน้อย 24 ชั่วโมง):** `yarn governance propose-unpause-v2 <POOL> true true true` เสนอผ่าน Squads
   รอ timelock ครบ แล้วรัน `yarn governance execute <ACTION_ID>` (ต้องทำภายใน 7 วัน)
   หลังจากนั้นเขียนรายงานสรุปเหตุการณ์ และจ่ายรางวัลให้คนที่แจ้งบั๊ก (ถ้ามี)

### กุญแจหาย (vault หรือกุญแจอัปเกรดถูกเจาะ)

ถ้าคนอื่นได้กุญแจอัปเกรดไป เขาจะใส่โค้ดอะไรก็ได้ รวมถึงโค้ดที่ลบปุ่มหยุดทิ้ง สิ่งที่ยังทำได้มีดังนี้
- กดหยุดทันที (ได้ผลถ้าโค้ดของเขายังไม่ได้ลบปุ่มหยุด)
- ประกาศเตือนผู้ใช้ให้เร็วที่สุด ทั้งบนเว็บและโซเชียล และบอกให้ถอนเงินถ้ายังถอนได้
- ใช้หลักฐานจากตัวเฝ้าดู hash ของแต่ละรุ่น และบันทึกของ OtterSec ยืนยันว่าโค้ดไหนเป็นของแท้

**การป้องกันคือทางเดียวที่ได้ผล:** กรรมการทุกคนใช้ hardware wallet · ตั้งเกณฑ์ 2-of-3 หรือ 3-of-5 · ตั้ง time lock ใน Squads · เปิดตัวเฝ้าดูพร้อม Telegram

## คำแนะนำเรื่อง time lock ของ Squads

ตอนนี้ multisig ถูกสร้างโดยมี time lock เป็น 0 แนะนำให้ตั้ง **12–24 ชั่วโมง**
ถ้ามีคนแอบเสนอการอัปเกรดที่ไม่ดี ทุกคนจะมีเวลาเห็นก่อนที่มันจะทำงานได้ ข้อเสียคือการย้อนรุ่นก็ต้องรอนานเท่ากัน
แต่ระหว่างที่รอ เรามีปุ่มหยุดฉุกเฉินช่วยกันเงินไว้แล้ว การเปลี่ยน time lock ทำผ่าน proposal ใน Squads

## สิ่งที่เจ้าของต้องทำ (ครั้งเดียว)

1. หลัง merge งานนี้ ให้ติด tag รุ่นแรกจาก main: `git tag program-v0.1.0 <commit> && git push origin program-v0.1.0`
   ระบบจะ build และสร้าง Release ให้เอง
2. **devnet:** อัปเกรด devnet ให้เป็นรุ่นจาก Release
   `bash scripts/rollback-program.sh prepare program-v0.1.0 --cluster devnet --keypair <กุญแจ devnet> --execute`
   (โปรแกรมบน devnet ตอนนี้ build ด้วย `anchor build` ธรรมดา hash จึงไม่ตรงกับรุ่นไหน ตัวเฝ้าดูจะเตือนจนกว่าจะทำข้อนี้)
3. ตั้งตัวแปรใน GitHub (Settings → Secrets and variables → Actions → Variables): `EXPECTED_AUTHORITY_DEVNET`
   ภายหลังตั้ง `MAINNET_PROGRAM_ID` และ `EXPECTED_AUTHORITY_MAINNET` (= ที่อยู่ Squads vault)
4. Telegram: สร้างบอทกับ @BotFather แล้วเพิ่มบอทเข้ากลุ่มส่วนตัว
   จากนั้นตั้ง secrets `ALERT_TELEGRAM_BOT_TOKEN` และ `ALERT_TELEGRAM_CHAT_ID`
5. บน mainnet ให้ deploy เฉพาะไฟล์ `swd_amm-mainnet.so` จาก Release ที่ hash ตรงกับรายงาน audit
   (ที่อยู่โปรแกรมถูกฝังอยู่ในโค้ด ตอนนี้เป็นที่อยู่ของ devnet ดังนั้นรุ่นสำหรับ mainnet ต้องติด tag บน commit ที่เปลี่ยนที่อยู่เป็นของ mainnet แล้ว)
6. ตั้ง time lock ใน Squads และมอบกุญแจฉุกเฉินให้คนที่เตรียมพร้อมรับเหตุ (on-call)

## ซ้อมทุกเดือนบน devnet (ประมาณ 1 ชั่วโมง ทุกวันจันทร์แรกของเดือน)

ซ้อมไว้ วันจริงจะได้ไม่ลน ให้จดผลลงใน GitHub issue ชื่อ "Rollback drill ปี-เดือน" ว่าใครทำอะไร และแต่ละขั้นใช้เวลากี่นาที

1. Actions → program-watch → Run workflow ผลต้องเป็นสีเขียว
2. รัน `bash scripts/rollback-program.sh status --cluster devnet`
3. กดหยุดพูลทดสอบบน devnet ด้วยกุญแจฉุกเฉินของ devnet
4. ย้อนไป **รุ่นก่อนหน้า**: `prepare <tag รุ่นก่อน> --cluster devnet --keypair <กุญแจ devnet> --execute`
   (ถ้าจะซ้อมให้เหมือนจริง ใช้ `--via-squads --vault <vault ของ devnet>` แล้วทำ proposal ใน Squads ด้วย)
5. รัน program-watch อีกครั้ง ต้อง **เตือน** เพราะบนเชนเป็นรุ่นเก่า แปลว่าระบบเตือนทำงาน (เช็กด้วยว่า Telegram ได้รับข้อความ)
6. ย้อนกลับมารุ่นล่าสุดด้วยวิธีเดียวกัน แล้วรัน program-watch ต้องเป็นสีเขียว
7. เปิดพูลกลับ: `propose-unpause-v2` รอ timelock (บน devnet ตั้งสั้นได้ถึง 5 วินาที) แล้ว `execute`
8. ขั้นไหนไม่ชัด ให้จดไว้และแก้คู่มือนี้
